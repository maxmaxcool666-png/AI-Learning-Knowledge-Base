# 多 AI 來源管理規則

## 以主題組織筆記

- 正式技術筆記按主題與分類整理，不按照 AI 平台拆分。
- 建立前先查閱總索引及分類資料夾；相同主題應整合，避免重複建立。
- 同一篇筆記允許記錄多個 AI 來源，保留各來源的貢獻與可追溯紀錄。

## 來源紀錄方式

來源可包含 ChatGPT（目前帳號）、ChatGPT（舊帳號）、Google Gemini、OpenAI Codex 與其他 AI 工具。以帳號角色區分 ChatGPT 來源即可，不記錄帳號個資。

每個來源應記錄平台、對話或資料日期（若可得）、主題、貢獻摘要與可公開的來源紀錄或參考連結。未知日期、缺少原文或無法取得連結時，直接標示缺漏，不補造資訊。不必為了追溯來源公開私人對話。

個人化記憶摘要只代表部分整理後的資訊，不能視為完整對話紀錄，也不能據此聲稱保留全部上下文或精確原文。

## 固定來源代號管理

| 來源代號 | 規劃的來源對應 |
| --- | --- |
| CHATGPT-01 | 最初使用的 ChatGPT 舊帳號 |
| CHATGPT-02 | 目前使用的 ChatGPT 帳號 |
| GEMINI-01 | 目前使用的 Google Gemini 帳號 |
| CODEX-01 | OpenAI Codex 操作與開發紀錄 |

1. 來源代號只用來追蹤來源，不代表實際帳號 ID。
2. 不記錄電子郵件、密碼、存取權杖或其他秘密資訊。
3. 已分配的代號不得因帳號角色變動而重新指派；表中的「目前」與「舊帳號」描述初始分配時的角色，後續角色變動仍保留原代號與來源對應。
4. 日後新增帳號或平台時，使用新的來源代號，不得與已分配的代號重複。
5. 來源代號只能識別來源，不能取代對話日期、主題及貢獻摘要。
6. 同一來源代號允許對應多次討論，但每次討論應保留可取得的日期及來源資訊，並在筆記的「AI 來源明細」中分別列出。
7. 如果無法確認歷史資料來自哪個帳號，不得猜測代號，應標示「來源待確認」。
8. 此代號表只代表目前規劃的來源對應，不代表已成功取得任何平台的歷史紀錄。

## 區分資訊與證據

- **AI 回答**：標記為 AI 建議或待查證說法，不直接視為已驗證事實。
- **官方文件**：記錄發布單位、文件連結、適用版本與查閱日期。
- **實作結果**：記錄實際環境、版本、步驟、日期與觀察結果。
- **個人推論**：標記為自己的理解或推測，與來源說法區分。

不同 AI 說法矛盾時，記錄差異、前提與版本，查閱官方文件並以適用環境實作驗證。查證前保留矛盾與待查證標記，不以平台名稱或多數說法直接決定正確答案。

## 驗證狀態

| 狀態 | 使用條件 |
| --- | --- |
| 待驗證 | 尚未查證，或缺少可支持結論的證據。 |
| 部分驗證 | 僅部分內容已確認；列出已驗證與待驗證範圍。 |
| 已驗證 | 所述範圍已有文件或實作證據支持，並記錄方法、日期與適用條件。 |

沒有驗證的資訊必須明確標示。文件比對與實作驗證分別記錄，只查閱文件不能宣稱完成操作。驗證結果不代表所有版本或環境皆成立；條件改變時重新評估狀態。

## 私人資料與公開規則

- 原始對話匯出、個資、密碼及 API 金鑰不得直接公開。
- 未來若需保留私人原始對話匯出，僅放入被忽略的 `local-private/`；本階段不建立或匯入原始對話資料。
- 正式筆記只能包含整理後且經敏感資訊檢查的內容；錯誤訊息、程式範例與來源連結也須檢查。
- `.gitignore` 不能移除已追蹤檔案，也不能阻止在其他檔案中寫入秘密；未來公開前仍須人工檢查。
