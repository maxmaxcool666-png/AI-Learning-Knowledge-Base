## 核心知識整理

### 本案例已回報實際採用的操作

- 作品集案例：Codex 回報只提交兩檔、格式檢查通過、Push 成功及 clean；後續 Git 報告另支持該 Commit 與兩檔變更。
- 知識庫案例：依轉交報告，先盤點、查證、建私人草稿、確認心得、唯讀審查，再限定正式歸檔的三檔變更。
- 知識庫的暫存、Commit 與 Push 分階段處理；本機 Commit 驗收後，才進行另行允許的 Push。
- 權限及部分 DNS 查詢失敗後，經使用者核准重試原命令；報告記載未自行改 ACL、憑證或相關設定。

以上均限於各案例回報範圍，不概括所有 Codex 工作。

### 根據案例整理的建議流程（一般建議／本次未操作）

1. 指定工作目錄、允許讀取與修改的檔案，列明禁止事項及完成條件。
2. 先唯讀盤點證據；不足時列缺口，不用一般教學補成歷史事實。
3. 將來源整理、草稿、使用者心得、安全審查、正式歸檔拆開驗收。
4. 修改後核對檔案差異、來源連結與內容，保留非任務範圍的既有修改。
5. 公開前檢查私人來源、秘密資料與 Commit 身分；忽略規則不能取代內容審查。
6. 暫存只指定核准路徑，審閱整個暫存區及相關檢查結果。
7. Commit 與 Push 分開授權；推送前確認遠端版本，成功後再核對 Hash。
8. 遇到權限或網路問題先停止，不自行擴權或更改設定；若有正常單次核准流程，取得使用者授權後才重試原命令。
9. 記錄執行結果、測試範圍與限制，使用者驗收後再進入下一階段。

本段是可重用方法，不表示早期作品集或其他任務均完整執行過。通過 diff 格式檢查也不等於沒有秘密或功能測試全部通過。

### 1. 最大的學習收穫

這次使用 Codex 的過程中，我了解到 Codex 可以協助我建立與修改程式碼，也能直接建立專案所需的文件。此外，我也學習到如何向 AI 更清楚地描述自己的需求，讓 Codex 能夠理解我想完成的工作。

### 3. 未來的應用方向

未來我希望能繼續運用 Codex 協助自己開發網站、製作專題、整理資料，以及檢查與生成程式碼，讓 Codex 成為我在開發與學習過程中的輔助工具。
