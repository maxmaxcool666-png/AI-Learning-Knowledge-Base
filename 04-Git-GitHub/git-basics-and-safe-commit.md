## 核心知識整理

### 工作目錄、暫存區與 Commit（C：一般知識）

- 工作目錄（working tree）是目前取出的檔案，可包含已追蹤檔案的修改與尚未追蹤的檔案。
- 暫存區（index／staging area）記錄下一次一般提交預計採用的內容，不是另一份遠端備份。
- 一般 `git commit` 以暫存區建立本機 Commit；檔案暫存後若再次編輯，後續修改不會自動進入同一次提交。
- Commit 記錄版本快照及歷史關係；不代表已推送、部署或通過測試。
- 在正確 Repository 與分支操作是前提。本機沒有未提交修改，不代表 GitHub 已同步。

### 指令用途與檢查範圍（C：一般知識）

| 指令 | 用途 | 限制與注意事項 |
| --- | --- | --- |
| `git status` | 檢視分支、暫存、未暫存與未追蹤檔案狀態 | 預設不列出忽略的檔案；遠端比較依本機已知參照，不是即時查詢 GitHub |
| `git diff` | 比較已追蹤檔案的工作目錄與暫存區差異 | 不呈現暫存區相對 HEAD 的差異，也不直接列出未追蹤檔案內容 |
| `git diff --cached` | 檢查暫存區相對 HEAD 的差異，即一般下一次提交的內容 | 仍須留意二進位檔案及未經實測的修改 |
| `git add -- "path/to/file"` | 將指定路徑目前的內容暫存 | 會改變暫存區；應先確認路徑及範圍，避免盲目使用 `git add .` |
| `git commit -m "訊息"` | 將暫存內容提交到本機 Repository | 不會自動推送；本筆記不以 `-a` 取代逐項檢查暫存範圍 |
| `git push origin main` | 請求將本機 main 推送至 origin 的 main | 會連線並可能修改遠端；必須先確認遠端、分支與待推送範圍，成功也不等於網站驗收成功 |

### 提交前檢查與安全範圍（C：流程建議）

1. 確認 Repository、分支與任務範圍，再看 `git status`。
2. 檢查工作目錄差異、未追蹤檔案，以及是否已有先前留下的暫存內容。
3. 排除無關修改、原始私人對話、密碼、API 金鑰、存取權杖與其他敏感資料。忽略規則不能保護已追蹤的秘密，也不能取代內容檢查。
4. 完成與修改相關的必要測試，分別記錄測試與 Git 結果，不將兩者混用。
5. 明確指定要暫存的路徑；暫存後再次核對檔案清單與完整差異。
6. 若發現非預期暫存內容，停止提交，先釐清保留方式；不要為了清空狀態刪除或覆蓋不明修改。
7. 提交前應看整個暫存區，而非只看剛加入的檔案；一般 commit 會包含既有暫存內容。
8. 提交後查看 working tree，推送另行確認，不將提交與推送視為同一步。

### git diff --check 的使用情境（C：一般知識）

`git diff --check` 可檢查差異是否引入衝突標記或依設定判定的空白錯誤，例如行尾空白；偵測到問題時會以非零狀態結束。

- `git diff --check`：檢查工作目錄相對暫存區的差異。
- `git diff --cached --check`：檢查暫存區相對 HEAD 的差異，適合提交前使用。
- 檢查範圍與一般 diff 類似，不應以此認定未追蹤檔案、所有二進位內容或全部檔案均已檢查。
- 沒有輸出或檢查通過，不代表程式正確、沒有秘密、所有衝突已處理或所有測試通過；仍需人工審查與適當測試。

### 提交後的 working tree 與遠端狀態（C：一般知識）

提交後使用 `git status` 檢查是否仍有暫存、未暫存或未追蹤檔案。一般所稱 clean 表示 Git 所報告的工作目錄與暫存區沒有待提交變更；不代表磁碟沒有忽略檔案，也不代表工作成果經過測試。

| 名稱 | 意義 | 不能據此推論 |
| --- | --- | --- |
| 本機 main | 本機分支參照，隨該分支提交而移動 | 不能單憑它確認 GitHub 目前內容 |
| HEAD | 通常指向目前分支，也可能處於 detached HEAD 狀態 | 不一定永遠等同 main |
| origin/main | 本機保存的 origin 遠端 main 追蹤參照，可因相關同步操作更新 | 不是 GitHub 伺服器的即時狀態 |
| GitHub 遠端伺服器 | 伺服器當時實際保存的分支與物件 | 本機參照一致或 working tree clean，均不足以確認它現在同步 |

`git status` 的 ahead／behind 判斷依本機已知追蹤參照。取得即時遠端資訊需要另外授權並執行連線查證；本次沒有執行。

### 建議操作範例（C；未執行）

以下是一般教學示例，不是使用者歷史操作，也不是 Codex 查證報告中的原始指令或輸出。本次沒有執行任何 Git 操作。

前提：已另行允許在目標 Git Repository 操作，確認所在分支及工作範圍。`path/to/intended-file.md` 與提交訊息均為佔位示例，需按實際任務替換。這不是要求現在初始化或操作本知識庫。

先檢查：

```sh
git status
git diff
git diff --cached
git diff --check
```

另外逐項閱讀未追蹤檔案；上述 diff 不會自動顯示其內容。確認修改與測試範圍後，才進行以下步驟：

```sh
git add -- "path/to/intended-file.md"
git status
git diff --cached --name-status
git diff --cached
git diff --cached --check
```

核對暫存區中每一項變更及敏感資訊。若檔案又被編輯，重新檢查並決定是否更新暫存，避免誤以為所有最新修改都已加入。檢查與測試符合要求後，才提交：

```sh
git commit -m "待替換：描述本次實際變更"
git status
```

檢視本次提交內容可另用：

```sh
git show --stat HEAD
git show HEAD
```

這些也是未執行的一般示例。若 working tree 不乾淨，先判斷剩餘內容是否屬於本次任務，不自動清除。

推送屬於另一步：先核對遠端 URL、目標分支及所有待推送 Commit，取得所需授權後，才考慮：

```sh
git push origin main
```

此指令假設目標確實是 origin 與 main，不能直接套用於任意專案。它可能推送多個尚未發布的 Commit，而非只推送剛建立的一筆；本次未執行。

## 個人心得

透過這次學習 Git 與 GitHub，我開始理解一些 Git 的基本操作指令，也學會如何利用 Git 進行版本管理。例如，透過 `git status` 查看哪些檔案有修改，以及了解本機與遠端版本的同步狀態。另外，我也學習到如何將專案上傳至 GitHub，讓程式碼可以保存在雲端。雖然目前許多操作仍是在 AI 的一步步引導下完成，但這個過程讓我逐漸了解 Git 與 GitHub 在專案開發中的用途。

在學習過程中，我覺得最困難的是記住 Git 指令及理解每個指令的用途。因為自己才剛開始接觸 Git，平常如果沒有經常使用，就很容易忘記指令的寫法或功能。遇到不熟悉的操作時，我通常需要重新上網查詢，或再次與 AI 討論來尋求協助。另外，Codex 的操作回報有時會出現一些我不理解的英文專業術語，也需要花時間進一步了解。

未來在其他專案開發中，我希望能持續運用 Git 進行版本管理，將不同階段的開發成果保存下來。這樣即使修改程式時發生錯誤，或是想嘗試新的功能，也能透過版本紀錄降低原有成果遺失的風險。此外，如果未來需要與其他人共同開發專案，我也希望能利用 Git 了解彼此修改了哪些內容，讓協作與版本管理更加方便。
